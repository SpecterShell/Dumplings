# Inno Setup architecture

Inno Setup is a compiler and a family of precompiled runtime programs. The output installer combines vendor-specific records and payloads with runtime binaries shipped with the Inno compiler.

## Main components

```text
ISCC / IDE
+-- preprocessor
+-- setup-script parser
+-- file enumerator and version reader
+-- Pascal Script compiler
+-- metadata serializer
+-- file compressor
`-- PE/resource/version/signing assembler

SetupLdr
+-- validates the outer installer
+-- reads the loader offset table
+-- handles early language/password/silent options
+-- extracts and verifies Setup.e32/e64
+-- starts the setup engine
`-- waits, forwards language/restart notifications, and cleans temporary files

Setup engine
+-- runs in setup, uninstaller, or RegSvr mode
+-- decodes setup-0 metadata
+-- selects language, architecture mode, and privilege mode
+-- hosts the wizard and Pascal Script VM
+-- filters and executes declarative records
+-- reads setup-1 or external disk slices
+-- records inverse operations
`-- creates uninstall files and ARP registration

Uninstaller
+-- uses the same compiled setup-engine family
+-- selects uninstaller mode from the PE header or command line
+-- reads the uninstall log and message data
+-- reloads uninstall-side Pascal Script
`-- replays inverse operations
```

## Precompiled runtime binaries

The compiler distribution contains precompiled files such as `SetupLdr.e32`, `SetupLdr.e64`, and setup-engine images. The compiler verifies these inputs, copies the appropriate loader, updates resources and PE flags, and embeds a compressed setup-engine image.

Current source calls the embedded engine `Setup.e32/64`. It is a complete PE image. SetupLdr restores its CALL-transformed bytes, validates `CRCEXE`, writes it to a temporary `.tmp` executable, and launches it.

The setup engine can select three modes:

- **Setup mode** when started by SetupLdr with `/SL5=` or when no alternate mode marker is present.
- **Uninstaller mode** when the command line contains `/UNINSTMODE` or the executable header contains `SetupExeModeUninstaller` at offset `0x30`.
- **RegSvr mode** when `/REGSVRMODE` or `SetupExeModeRegSvr` selects the registration helper path.

This reuse explains why the uninstaller contains much of the same runtime and scripting surface as Setup.

## Output families

### Normal single-file output

```text
Setup.exe
+-- SetupLdr
+-- setup-0 metadata
+-- compressed setup engine
`-- setup-1 file payloads
```

This is the common downloadable installer. `Offset0`, `OffsetEXE`, and `Offset1` all point inside the same file.

### Output without SetupLdr

With `UseSetupLdr=no`, the compiler writes the prepared setup engine as the `.exe`. Metadata and payload are adjacent files:

```text
Setup.exe       actual setup engine
Setup-0.bin     metadata and file-location records
Setup-1.bin     payload chunks
```

The setup engine derives `Setup-0.bin` from its own base filename when it was not started with `/SL5=`.

### Disk-spanning output

Disk-spanning media separates payloads into `Setup-*.bin` slices. The outer offset table uses `Offset1 = 0`, and setup resolves slice files through disk headers and media-selection logic.

```text
Setup.exe
+-- SetupLdr
+-- setup-0 metadata
`-- compressed setup engine

Setup-1.bin ... Setup-N.bin
`-- disk slice header + payload ranges
```

File-location records store `FirstSlice`, `LastSlice`, and a start coordinate. Setup can prompt for media or locate the next slice. Nonzero slice numbers refer to external media and are not offsets in `Setup.exe`.

## SetupLdr and the setup engine communicate through `/SL5=`

SetupLdr launches the restored setup engine with an internal parameter containing:

```text
/SL5="<loader-window-handle>,<Offset0>,<Offset1>,<original-installer-path>"
```

The setup engine uses these values to:

- reopen the original installer instead of its temporary engine file;
- seek directly to setup-0 metadata;
- locate the embedded setup-1 payload;
- preserve the original source directory and filename;
- notify SetupLdr when language changes or a restart is requested.

The exact internal parameter is not a public silent-install switch. It is generated by SetupLdr and contains process-specific state.

## Process and privilege topology

Setup can involve more than two processes:

```text
original SetupLdr
`-- temporary setup engine
    `-- elevated respawn of Setup or SetupLdr, when required
        `-- child programs from [Run], registration, or script code
```

The initialization path reads the setup header before deciding whether elevation is needed. It may apply `/CURRENTUSER` or `/ALLUSERS`, previous-install scope, or a dialog selection. If the effective privilege mode requires elevation, the process respawns through the elevation path and forwards non-internal command-line parameters.

Setup maintains an "original user" execution path for actions such as `runasoriginaluser`, even when the main setup process is elevated.

## Logical data sets

The compiler creates three logical data sets:

1. **Setup-0 metadata:** identity, directives, language data, record tables, wizard images, decompressor support data, and file-location entries.
2. **Setup engine:** a precompiled PE runtime image, compressed independently from package payloads.
3. **Setup-1 payloads:** source files grouped into stored or compressed chunks, optionally solid-compressed or encrypted.

The name `setup-0` refers to the logical metadata data set even when it is embedded in `Setup.exe`. The name `setup-1` similarly refers to the first payload slice.

## Shared structures versus in-memory objects

`Shared.Struct.pas` declares packed records shared by the compiler, setup engine, loader, and uninstaller. Many records contain Delphi `String` and `AnsiString` fields. Their in-memory pointer values are never serialized directly.

`SECompressedBlockWrite` writes:

1. every declared Unicode/string field as a length-prefixed byte sequence;
2. every declared ANSI string similarly;
3. the packed non-string tail from the record after skipping the in-memory string slots.

`SECompressedBlockRead` reconstructs a runtime record by allocating strings and copying the fixed tail. Disk layout sizes therefore differ from `SizeOf(TRecord)` by the architecture-dependent string-pointer region.

## Architecture terminology

Inno uses several unrelated architecture decisions:

| Term | Controls |
| --- | --- |
| SetupLdr architecture | Whether the outer loader is a 32-bit or 64-bit PE. |
| Setup engine architecture | Whether `Setup.e32` or `Setup.e64` runs. |
| `ArchitecturesAllowed` | Whether setup can run on the current processor/OS architecture. |
| `ArchitecturesInstallIn64BitMode` | Whether 64-bit file-system and registry views become the default for entries and constants. |
| Entry `Bitness` | Per-file, registry, run, or registration override. |
| Payload architecture | Architecture of the application binaries being installed. |

These values can differ. A 32-bit loader can install x64 files. An entry can force a 32-bit registry view during a 64-bit-mode install. Package architecture must come from the supported target behavior and installed binaries, not from the outer PE alone.
