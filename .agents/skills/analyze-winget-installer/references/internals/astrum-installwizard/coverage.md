# Astrum InstallWizard coverage

Coverage is structural. A checked capability means the parser has a bounded implementation and a distinct fixture; it does not mean every custom condition or external child effect is statically knowable.

## Remaining limits

| Gap | Current handling | Evidence needed |
| --- | --- | --- |
| Nonzero 1.x operation-tail words | retain `ObservedOperationTail` | one-option controlled 1.x builds plus runtime-path confirmation |
| Legacy1 and Early2 option tails | retain bounded `OptionBlockEvidence` | paired projects or source-backed runtime tables for each profile |
| Nonempty 2.x post-interactive records | parse framing and emit incomplete-semantics diagnostic | populated project plus observed runtime effect |
| Typed dialog and image resources | export bounded pre-catalog ranges | record grammar from controlled builds or runtime code |
| Astrum 1.x spanned media | reject | one complete ordered 1.x volume set |
| Early2 User Information behavior | retain documented interactive-only result | VM installation of a controlled Early2 dialog fixture |
| Releases before 1.80 or after 2.29.50 | accept only when an existing route validates exactly | structurally distinct builder/runtime media |
| Dynamic variables and external DLL effects | preserve source records and unresolved fields | source inspection or VM validation for the exact artifact |

These limits protect WinGet matching. Unknown bytes are not converted into ProductCode, scope, elevation, switch, or installed-file claims.

## Validation expectations

A footer or catalog change needs valid, truncated, overlapping, and oversized cases. A configuration-field change needs a controlled builder diff and a fixture from every profile it claims to support. An ARP, scope, elevation, or switch change needs installed-state evidence when runtime context affects the result. Extraction changes need stored, GZip, signed, tiny, spanned, collision, traversal, and aggregate-limit coverage.
